# HANDOFF для Claude Code

LED-бейдж 11x44 на **WCH CH582M**. Состояние на 2026-09-06, 10:40 — всё работает, кнопки приходят событиями.
Каждый факт здесь либо снят с устройства, либо прочитан в исходниках.
Где не проверено — так и написано.

## СДЕЛАНО 2026-09-06: кнопки как события по BLE

Прошивка — ветка `feat-button-events` форка (= `hw-rev2-t-b6` после
fast-forward), четыре коммита поверх исправления `ng_notify()`:

1. `button.c`: `btn_onPress`/`btn_onRelease` — дебаунсированные фронты на том
   же автомате, плюс геттеры `btn_getOnePress`/`btn_getLongPress`.
2. `main.c`: в стриминге события `E0 01/81/02/82` через `ng_notify`; долгий
   `KEY2` — выход в меню с `E0 00`; защита от повторного входа.
3. `main.c`: при входе в стриминг останавливаются `CLOCK_TICK`/`STOPWATCH_TICK`
   (лечит ловушку 6a).
4. `BadgeBLE.md`: раздел «Buttons while streaming».

Клиент `rpi/`: `Keys` в `badge/ble.py` (автоподписка на `F056`), `self.keys`
у источников, `badgectl keys`, `GET /keys`, `badge_keys` в MCP, платформер с
прыжком по `KEY1`: до первого реального нажатия — автопилот (чтобы с прошивкой
без событий герой не застыл у трубы), `auto=1` — автопилот навсегда.
Демон при `E0 00` останавливает поток и очищает источник; SIGINT/SIGTERM —
штатная остановка с выходом из стриминга и отключением (проверено: 0.6 с),
второй сигнал — жёсткий выход. Оффлайн-тест `rpi/test_offline.py`.

Измерено на железе: 61 событие без потерь, удержания от 90 мс, хост 0.1–0.3 мс,
квантование 30 мс = интервал соединения; полный круг оценочно 50–100 мс, прямо
не измерен. Выход долгим `KEY2` проверен.

## СЛЕДУЮЩИЙ ШАГ

1. PR в апстрим: четыре коммита `feat-button-events` перенести на `master`
   (они не зависят от патчей пина и MTU), один PR — одна тема: события кнопок.

## ГЕЙТ: НИ ВЫВОДА, НИ РЕЛИЗА, НИ ПУША БЕЗ АУДИТА (правило Николая 2026-09-06)

Любой код — свой или правка чужого — до того как назвать его готовым,
закоммитить, запушить, выложить в PR или построить на нём вывод, проходит
агент `senior-code-audit`. Вердикт `CHANGES-REQUIRED` = работа не закончена.
Зелёный CI аудитом не является: CI проверяет, что собирается, а не что верно.

**Чем оплачено.** PR #193/#194 в апстрим ушли без аудита. Боты-ревьюеры
нашли два бага и пробел в документации. Первый раунд правок был сделан,
НЕ ПРОЧИТАВ ревью целиком, — и опять без аудита. Аудит, запущенный после,
вернул `CHANGES-REQUIRED` и нашёл сверх ботов, в том числе двойное
освобождение буфера в `ng_notify()` (`src/ble/profile/ng.c`), которое
сидит в master и подтверждено примером WCH — освобождать только при неудаче
`GATT_Notification`.

**Порядок для GitHub** (issue, PR, ответы на ревью):

1. Сначала прочитать ВСЁ обсуждение: каждый комментарий каждого ревьюера
   целиком, включая свёрнутые «outdated». Не чинить по заголовкам.
2. Каждое замечание проверить ОПЫТОМ до ответа: тезис бота бывает ложным
   (Copilot про brace expansion внутри `${{ }}` — проверено, неверно).
   «Исправлено» — только с SHA коммита; «не согласен» — только с доказательством.
3. Диф трассировать до потребителя. Новый вариант сборки — это Makefile →
   workflow → артефакт → README → ссылка на бинарник. Одного файла не бывает.
4. Один PR — одна тема. Найденное попутно, даже HIGH, — отдельный issue или
   отдельный PR со ссылкой, не довесок.
5. Аудит → CI на черновой ветке форка → force-push в ветку PR → комментарий
   в PR. Именно в этом порядке. Черновые ветки удалять после.
6. Коммиты по правилу репозитория: заголовок ≤ 72, тело объясняет «почему»,
   ссылка на первоисточник, если правка опирается на чужое соглашение.

**Инструменты под этот порядок** — готовые скиллы в `~/.claude/skills`, выбраны
2026-09-06 после поиска по девяти источникам (свой не писали намеренно):
`receiving-code-review` и `verification-before-completion` (superpowers, MIT),

## Что сейчас на бейдже

Прошивка: форк badgemagic, ветка `hw-rev2-t-b6` = `feat-button-events`
(коммит `f1d2a06`): **два обязательных патча**, исправление `ng_notify()` (#196)
и события кнопок. Файл `firmware/badgemagic-usb-c-2key-tb6-btnevents.bin`,
sha256 `5a58cc27…`, прошит 2026-09-06 10:27 (`Verify OK`), проверен: события
61/61, платформер по кнопке.
Откат: `firmware/badgemagic-usb-c-2key-tb6-mtu128-notifyfix.bin` (`14784f6a…`,
без событий), затем `…-mtu128.bin` (`58a81181…`), затем `…-tb6-PREV.bin`.

**Патч 1 — пин матрицы.** `LED_PIN_T_B6`: пин `T` = `B6` отдельно от `J` и `K`.
У этой платы `T` как в REV3, а `J`/`K` как в дефолте — такой комбинации среди
готовых сборок нет. Без патча мертвы колонки 38–39; `usb-c-4key` (REV3) убил бы
вместо них 18–21.

**Патч 2 — потолок MTU.** `BLE_BUFF_LEN` `64+4` → `128+4` плюс
`GATT_PROP_WRITE_NO_RSP` на `F057`. Кадр 89 байт теперь идёт одной ATT-посылкой.
**Один только WRITE_NO_RSP бесполезен**: `Write Command` ограничен `ATT_MTU-3`
и длинной формы не имеет.

**Исправление `ng_notify()` уже на бейдже** (cherry-pick `663b05c`+`77cdbad`
в `hw-rev2-t-b6`, прошито 2026-09-06). Суть: буфер уведомления освобождать
только при неудаче `GATT_Notification`, как в примере WCH. В апстрим — PR #196.
Чего в прошитой ветке НЕТ: правок второго раунда из PR #193/#194 (ошибки
протокола через notify, проверка `BLE_LibInit`, защита Read Blob) — они в
ветках `pr-*`, на работу стриминга не влияют.

Собирать только из форка:
https://github.com/NickoScope/badgemagic-firmware/tree/hw-rev2-t-b6
CI собирает вариант `usb-c-2key-tb6`; локальный RISC-V тулчейн не нужен.

Настройки в EEPROM: `always-on BLE` включён, `SECURITY` включена,
ребут после приёма выключен.

## Что требует сопряжения и кода

| Что | Профиль | BT-PAIRING | PIN |
|---|---|---|---|
| Стриминг, яркость, настройки | next-gen F055/F057 | нет | нет |
| Загрузка картинки, установка часов | legacy FEE0/FEE1 | **да** | **да** |

Гейт `!authorized` стоит только в `legacy_ble_rx()`. Код генерируется заново при
каждом входе в `BT-PAIRING` и сбрасывается при разрыве связи
(`legacy_reset_auth()` в `src/ble/peripheral.c`) — значит **PIN и данные должны
уйти в одном соединении**.

Бейдж рекламируется постоянно благодаря `always-on BLE`; настройка живёт в Data
EEPROM и переживает перепрошивку кодового флеша.

## Часы

RTC ставится **только по BLE**, из поля `timestamp` заголовка `wang`
(`src/legacyctrl.c`). В `legacy_usb_rx()` вызова `RTC_InitTime` НЕТ.

1. Меню → `BT-PAIRING`, прочитать 4 цифры
2. `./synctime <PIN>`
3. Меню → `CLOCK MODE` → `TIME`

**Повторять после каждой перезагрузки бейджа**: `tmos_clockInit()` безусловно
вызывает `RTC_InitTime(2020, 1, 1, 0, 0, 0)`.

## Стриминг

Next-gen профиль: `streaming_setting` (0x02), `stream_bitmap` (0x03).
Пишет ПРЯМО в фреймбуфер — **износа флеша нет**, гонять можно сутками.

Кадр: 44 слова по 16 бит little-endian, бит 0 = верхний пиксель, значимы 0..10.
Полный кадр = 1 + 88 = 89 байт.

Измерено после патча MTU: **30.0 fps, вся панель, без разрывов и обрывов**
(1440 кадров за 48 с). До патча было 4.7 fps и обрыв каждые 25–30 с.
30 — потолок, заданный клиентом (`BADGE_FPS`), не предел железа.

**КЛИЕНТ ОБЯЗАН ЗАДАВАТЬ ТЕМП.** При записи без подтверждения обратной связи нет;
без ограничения цикл забивает очередь macOS — наблюдалось 86000 «кадров»/с
и зависание на 22 с.

Переменные: `BADGE_FPS`, `BADGE_LOOP`, `BADGE_STREAM_MODE` (`full44`/`hybrid`/`fast30`),
`BADGE_FULL_EVERY`.

## Ловушки

**1. macOS убивает Python при обращении к CoreBluetooth.** `Abort trap: 6`,
namespace TCC: ни у системного, ни у brew-Python нет
`NSBluetoothAlwaysUsageDescription`. Решение — подписанная копия `Python.app`
с этим ключом, запускаемая **через LaunchServices** (`open -W -a`). Из shell
напрямую НЕ помогает: TCC винит родительский процесс. Всё в `setup.sh`.

**2. `find_library('hidapi')` не смотрит в `/opt/homebrew/lib`.** Лечится
`DYLD_FALLBACK_LIBRARY_PATH`.

**3. Пакеты обязаны быть кратны транспорту.** `legacy_ble_rx()` отвергает пакет
длиной != 16, а завершение передачи (и `RTC_InitTime`) наступает на ПОСЛЕДНЕМ
пакете — короткий хвост означает молча не выставленные часы. По USB `lednamebadge`
шлёт `range(len(buf)/64)` и хвост ОТБРАСЫВАЕТ. Дополнение нулями сделано
в `badge_ble.py` и `badgex.py` — не убирать.

**4. Двоеточие в `lednamebadge` — синтаксис иконок.** `":18:"` → `chr(18)` →
`IndexError`. Падает **в зависимости от минуты**: `chr(26)` и `chr(0)` случайно
работают, `chr(18)` и `chr(2)` нет. Поэтому часы шли весь вечер и сломались
внезапно. Рисовать посимвольно через `bitmap_char()` — так сделано в `text_cols()`.
Заведено: ls32 issue #22.

**5. Байт 5 заголовка — индекс уровня яркости, не маска.** Уровней 4:
`0x00`/`0x10`/`0x20`/`0x30`. Апстрим шлёт `0x40` для 25% — портит изображение.
Обойдено в `fix_brightness()`.

**6a. Перед стримингом выйти из `CLOCK MODE`.** Часы перерисовываются поверх
стримингового кадра каждую секунду — на экране «моргает мусор» на всех сценах,
хотя хост видит 30 fps и ноль обрывов (2026-09-06, первый прогон после
прошивки). Тот же механизм, что у меню по кнопкам, см. IDEAS.md. Лечится
только на бейдже: другой режим, затем стриминг.

**6. Успешная запись ничего не доказывает.** Подтверждения от прошивки нет.
Единственная проверка — попросить человека посмотреть на экран.
Не выдавать «отправлено» за «сработало».

## Опасности

**Анимация длиннее ~60 кадров делает бейдж незагружаемым.** Измерено: 120 кадров
(7.3 КБ) → при распаковке слота одновременно живут сырой кусок 7260 байт
и распакованный битмап 10560 байт, ~17.8 КБ при 32 КБ SRAM с 6 КБ под BLE.
`malloc` возвращает NULL, `data_flash2newmem()` его не проверяет — прошивка виснет
в `load_bmlist()`, экран замирает на заставке. Хранилище ни при чём.
Безопасно 40–60 кадров. Стриминг ограничений не имеет.
Заведено: issue #195.

**`data_flatSave()` пишет с нуля без проверки границ.** В той же EEPROM лежат
`badge_cfg` и рекорд игры — длинная загрузка их затрёт.

**USB после перепрошивки не поднимается** (4 замера). В ISP — работает, значит
кабель исправен. `./badge` и `./badgex` применимы только к заводской прошивке.
Совпадает с апстримным issue #152, подтверждение отправлено.

## Восстановление, если бейдж завис на заставке

Программный вход в ISP НЕ работает: `SCAN_BOOTLD_BTN` регистрируется
в `spawn_tasks()`, до которой выполнение не доходит. Нужен аппаратный:

1. отключить батарею, зажать `KEY2`, воткнуть USB; **либо**
2. USB воткнут, зажать `KEY2`, кратко замкнуть и отпустить `C3`

Затем `./fix_eeprom.sh` — ждёт ISP, стирает EEPROM, сбрасывает устройство.
Кодовый флеш не трогает.

Вместе с плохой анимацией сотрутся настройки. Возврат:
меню → `SECURITY` → `ENABLE`, меню → `BT-PAIRING`, затем `restore_cfg.py`.

## Чего НЕ делать без явного разрешения человека

* `wchisp config reset`, `flash`, `erase` — необратимо
* прошивать не тот вариант: неверная ревизия ломает изображение,
  неверный `KEY_COUNT` — навигацию (железу не вредит)
* релиз `v0.1` для USB-C не годится: он «micro-USB only»
* ветка `bin` апстрима отстаёт (пуш в неё падает на правиле репозитория);
  брать артефакты CI

## Не проверено

* Чтение `FEE1` возвращает `04 00 00…` при любом режиме. Гипотеза «первый байт =
  номер режима» ПРОВЕРЕНА И ОПРОВЕРГНУТА. Что это — неизвестно.
* Notify на `FEE1` включается, но за сессию не прислал ни пакета.
* Год в RTC декодируется как `2000 + ((ts[0] - 208 + 256) % 256)`, наш инструмент
  пишет `year % 100` — год неверный. На `HH:MM` не влияет.
* Режим 10 (Rotate) отдельно не проверялся; режим 9 даёт пустой экран.
* Точная граница длины анимации между 60 и 120 кадрами — мерить не стали,
  цена ошибки слишком высока.
* Потолок fps стриминга: 30 задано клиентом, запас не измерялся.

## USB после перепрошивки: непрерывная запись перехода

Замер 2026-09-05 23:39, шаг 0.25 с, без единой команды устройству:

```
+0с    4348:55e0   загрузчик
+7с    ПУСТА       ISP истёк, стартовала прошивка
+40с   4348:55e0
+50с   ПУСТА
+65с   4348:55e0
+75с   ПУСТА
+94с   4348:55e0
+104с  ПУСТА
```

104 секунды, четыре окна ISP, около минуты работы прошивки между ними -
`0416:5020` не появился ни разу. Значит не «отваливается позже» и не «не реагирует
на горячее подключение», а **не поднимается вовсе**. Кабель и порт исправны:
в той же записи загрузчик перечисляется четырежды.

По коду проверено и признано корректным: тактирование `PLL_60MHz`, порядок вызовов
(`usb_start()` второй в `main()`), инициализация в `src/usb/setup.c`
(`RB_PIN_USB_DP_PU`, `RB_UD_PORT_EN`, `RB_UC_DEV_PU_EN`, разрешение прерываний,
`PFIC_EnableIRQ(USB_IRQn)`), наличие `USB_IRQHandler` в `src/usb/ctrl.c`,
отсутствие сна вне `poweroff()`.

Дальше без приборов не продвинуться: нужен UART-лог 921600 (в `ctrl.c` каждое
прерывание печатает `usb: new interrupt`), то есть переходник и вскрытие корпуса.
Запись добавлена в апстримный issue #152.

**Следствие для стриминга по кабелю:** он потребовал бы ДВУХ правок - починить
перечисление и проложить маршрут от USB к `ng_parse`. Сейчас оба USB-канала
заведены на `legacy_usb_rx`, а `ng_parse()` вызывается только из
`src/ble/profile/ng.c`. По BLE при этом 30 fps на всю панель.

**Грабля инструмента:** `wchisp reset` (и финальный сброс в `wchisp flash`)
может зависнуть навсегда, ожидая ответа от чипа, который уже ушёл в прошивку —
запись при этом давно завершена. `flash_tb6.sh` с 2026-09-06 держит сторожа
30 с и судит по `Verify OK` в логе, а `grep` в нём небуферизованный.


## Хранимая анимация — работает без компьютера

```bash
open -W -a ./BLEPython.app --args "$PWD/make_film.py" --pin XXXX --speed 6
```

48 кадров, четыре движения по 12: пульсирующее сердце, бегущая синусоида,
расходящиеся круги, летящие искры. Каждое зациклено само в себе.

```
2112 столбцов, 264 байт-столбца, 2976 байт, 186 пакетов, ~16 с заливки
RAM при распаковке ~7.0 КБ
```

**Предел подтверждён с двух сторон:** 48 кадров (~7 КБ RAM) ложатся спокойно,
120 кадров (~17.8 КБ) роняют загрузку. Оценка «40-60 безопасно» — измерение,
а не догадка. В `make_film.py` стоит стоп на 8000 байт.

После заливки: меню -> `ANIMATION`. **Mac не нужен** — фильм во флеше, играет сам.

Без компьютера работают: хранимая анимация, часы `CLOCK MODE`, секундомер, игры.
Стриминг — нет, он по определению поток с хоста: отключишь Mac, картинка замрёт
на последнем кадре.
