# HANDOFF для Claude Code

Проект: управление LED-бейджем 11x44 на WCH **CH582M** с macOS.
Состояние на 2026-09-05: **всё работает.** Бейдж перепрошит на badgemagic,
часы идут от RTC, инструменты в репозитории.

Этот файл — то, что сэкономит следующей сессии несколько часов. Каждый факт здесь
проверен на живом устройстве или прочитан в исходниках. Где не проверен — так и написано.

## Ловушки, каждая стоила времени

**1. macOS убивает любой Python при обращении к CoreBluetooth.**
`Abort trap: 6`, termination namespace TCC. Ни у системного, ни у brew-Python нет
`NSBluetoothAlwaysUsageDescription`. Решение — подписанная копия `Python.app` с этим
ключом, **запускаемая через LaunchServices** (`open -W -a`). Запуск из shell напрямую
НЕ помогает: TCC винит родительский процесс. Всё в `setup.sh` и обёртке `badgeble`.

**2. `ctypes.util.find_library('hidapi')` не смотрит в `/opt/homebrew/lib`.**
Лечится `DYLD_FALLBACK_LIBRARY_PATH`. В обёртках `badge` и `badgex`.

**3. Пакеты обязаны быть кратны размеру транспорта.**
`legacy_ble_rx()` отвергает любой пакет длиной != 16 байт. Завершение передачи
(и `RTC_InitTime`) наступает на ПОСЛЕДНЕМ пакете — короткий хвост означает, что
данные приняты частично, а часы молча не выставились. По USB та же беда с другой
стороны: `lednamebadge.py` шлёт `range(len(buf)/64)` отчётов и хвост ОТБРАСЫВАЕТ.
Дополнение нулями сделано в `badge_ble.py` и `badgex.py` — не убирай.

**4. Байт 5 заголовка — индекс уровня яркости, не битовая маска.**
Уровней четыре: `0x00`=100%, `0x10`=75%, `0x20`=50%, `0x30`=25%.
Апстрим `led-name-badge-ls32` шлёт `0x40` — это индекс 4 в таблице из 4 элементов,
изображение портится вместо затемнения. Обойдено функцией `fix_brightness()`.

**5. Бейдж перезагружается после каждой записи** (на заводской прошивке).
Видно как смена HID-пути по USB и как разрыв BLE с паузой рекламы 10-30 с.
`lednamebadge.py` при пропаже устройства делает `sys.exit` и убивает любой цикл —
в `badgex.py` это закрыто через `wait_for_device()` и `send_retry()`.

**6. Успешная запись ничего не доказывает.** Ни по USB, ни по BLE нет подтверждения
от прошивки. Единственная проверка — попросить человека посмотреть на экран.
Не выдавай «отправлено» за «сработало».

## Часы: точный порядок

Часы читают RTC чипа. RTC ставится **только по BLE**, из поля timestamp заголовка
`wang` (`src/legacyctrl.c`). В `legacy_usb_rx()` вызова `RTC_InitTime` НЕТ —
по USB картинку залить можно, часы выставить нельзя.

BLE требует авторизации, а код появляется только при **включённой** защите
(см. issue #190 — при выключенной загрузка вообще невозможна). Поэтому:

1. На бейдже: меню -> `SECURITY` -> `ENABLE`
2. Меню -> `BT-PAIRING` -> на экране 4 цифры
3. `./synctime <PIN>` — код и данные уходят В ОДНОМ соединении
   (`legacy_reset_auth()` обнуляет флаг при каждом разрыве)
4. Меню -> `CLOCK MODE` -> `TIME`

Повторять после каждой перезагрузки бейджа: `tmos_clockInit()` безусловно вызывает
`RTC_InitTime(2020,1,1,0,0,0)` при старте.

Перед синхронизацией стоит один раз отключить ребут после приёма, иначе бейдж
перезагрузится сразу после установки времени и обнулит его:
`power_setting` = `01 01 00`, затем `save_cfg` = `06`, в характеристику F057.
Байты взяты ИЗ КОДА `ngctrl.c` — документация инвертирована (issue #191).

## Чего НЕ делать без явного разрешения человека

* **`wchisp config reset`** — снимает защиту и СТИРАЕТ флеш. Точка невозврата.
* **`wchisp flash` / `erase`** — то же самое.
* Прошивка **не той сборки**: вариантов четыре (`usb-c`/`micro-b` x `2key`/`4key`),
  отличается разводка пина матрицы. Неверный `KEY_COUNT` не ломает железо
  (только навигацию), неверная ревизия платы — ломает изображение.
* Релиз `v0.1` не годится для USB-C: он «micro-USB only».
  Брать сборку из артефактов CI (ветка `bin` отстаёт: пуш в неё падает
  на правиле репозитория, сам код собирается нормально).

## Что осталось непроверенным

* **Чтение `FEE1`** возвращает `04 00 00 ...` — стабильно, при разных режимах одинаково.
  Гипотеза «первый байт = номер режима» проверена и ОПРОВЕРГНУТА. Что это — неизвестно.
  `badge-studio` утверждает, что канал чтения молчит; у нас отвечает.
* **Notify на FEE1** включается без ошибки, но за сессию не прислал ни пакета.
* **Год в RTC** декодируется как `2000 + ((ts[0] - 208 + 256) % 256)`, а наш инструмент
  пишет `year % 100` — год получается неверный. На `HH:MM` не влияет, не чинили.
* Режим 10 (Rotate) на CH582M отдельно не проверялся; режим 9 даёт пустой экран.

## Стриминг (stream_demo.py)

Next-gen профиль F055/F057, команды `streaming_setting` (0x02) и `stream_bitmap` (0x03).
Пишет ПРЯМО в фреймбуфер — износа флеша нет. **Авторизация не нужна**, гейт
`!authorized` только в `legacy_ble_rx()`. Только BLE: от USB пути к `ng_parse` нет.

Кадр: 44 слова по 16 бит little-endian, бит 0 = верхний пиксель, значимы 0..10.

Измерено: 30 столбцов (61 байт, одна ATT-посылка) = 10.6–16.2 fps, стабильно 41 с.
44 столбца (89 байт, длинная запись) = 2.7–4.9 fps И РАЗРЫВ через 25–30 с —
длинные записи исчерпывают `BLE_BUFF_NUM`, о чём предупреждает комментарий в
`src/ble/setup.c`. Причина: `F057` без `GATT_PROP_WRITE_NO_RSP` (issue #192).
Поэтому по умолчанию `BADGE_STREAM_COLS=30`.

## ВАЖНО: у этой платы нестандартный пин матрицы

Пин `T` (`led_pins[19]`, пара развёртки 19, колонки 38-39) должен быть **B6**, как в
`HARDWARE_REV3`, а `J` и `K` — дефолтные B15/B14. Готовой сборки с такой комбинацией нет.
Собирать только из форка с `LED_PIN_T_B6=1 KEY_COUNT=2`:
https://github.com/NickoScope/badgemagic-firmware/tree/hw-rev2-t-b6

Прошито `firmware/badgemagic-usb-c-2key-tb6.bin`. Обычный `usb-c-2key` оставит
две колонки мёртвыми, `usb-c-4key` (REV3) убьёт вместо них шесть.

Метод, которым это нашлось: `diag_edge.py` зажигает ровно две колонки за раз,
`diag_blocks.py` — пять блоков по 4 колонки с промежутками по 5. Человек отвечает
«горит / не горит». Никаких рассуждений о транспорте — они увели на полтора часа
в сторону (грешил на длинные записи, потерю ATT-фрагмента, паддинг и ревизию целиком).

## Прошивка: два наших патча (ОБА обязательны)

Форк https://github.com/NickoScope/badgemagic-firmware/tree/hw-rev2-t-b6

1. `LED_PIN_T_B6` - пин T матрицы = B6 отдельно от J и K. Без него мертвы колонки 38-39.
2. `BLE_BUFF_LEN` 64+4 -> 128+4 и `GATT_PROP_WRITE_NO_RSP` на F057.
   Без подъёма MTU кадр 89 байт не влезает в ATT-запись (61 байт при MTU 64) и уходит
   длинной записью: 4.7 fps и обрыв каждые 30 с. С правкой - 30 fps на всю панель.
   ВНИМАНИЕ: один только WRITE_NO_RSP бесполезен - Write Command ограничен MTU-3
   и длинной формы не имеет.

Актуальный бинарь: `firmware/badgemagic-usb-c-2key-tb6-mtu128.bin` (sha256 58a81181…).
Откат: `firmware/badgemagic-usb-c-2key-tb6-PREV.bin`.

КЛИЕНТ ОБЯЗАН ЗАДАВАТЬ ТЕМП: при записи без подтверждения обратной связи нет,
цикл забивает очередь macOS (наблюдалось 86000 «кадров»/с и зависание на 22 с).

## BT-PAIRING нужен НЕ ВСЕГДА

Проверено 2026-09-05: бейдж рекламируется постоянно, без входа в режим сопряжения.
Причина - включённый и сохранённый `always-on BLE` (`ble_setting [04 00 01]` + `save_cfg`).
Настройка живёт в **Data EEPROM**, отдельной от кодового флеша, поэтому пережила
обе перепрошивки: `wchisp flash` пишет только код, `config reset` трогает регистры чипа.

| Что делаем | Профиль | Нужен BT-PAIRING | Нужен PIN |
|---|---|---|---|
| Стриминг `stream_bitmap` | next-gen F055/F057 | **нет** | **нет** |
| Яркость, настройки, `save_cfg` | next-gen F055/F057 | **нет** | **нет** |
| Загрузка картинки `wang` | legacy FEE0/FEE1 | **да** | **да** |

Гейт `!authorized` стоит только в `legacy_ble_rx()`. Next-gen профиль его не проверяет,
поэтому всё потоковое и конфигурационное работает с любого места - хоть из меню,
хоть из режима ANIMATION.

BT-PAIRING остаётся нужен лишь для обычной загрузки картинок: только там генерируется
четырёхзначный код, без которого `legacy_ble_rx()` отвергает пакет с `wang`.
Поэтому и синхронизация часов (`./synctime`) по-прежнему требует кода - RTC ставится
именно из legacy-заголовка.


## ВНИМАНИЕ: после перепрошивки USB не работает

Проверено 2026-09-05, четыре независимых замера. Это **цена перепрошивки на badgemagic**,
о которой стоит знать заранее.

| Состояние | Обычный режим | ISP (долгий KEY2) |
|---|---|---|
| Заводская прошивка | `CH583` на шине, `./badge` работал | — |
| badgemagic | **пусто, 0 устройств** | устройство есть, чип читается |

Кабель и порт исправны — это доказано тем, что в ISP устройство определяется
на том же кабеле. Бейдж при проверке был заведомо включён и разбужен.

Воспроизведено на трёх сборках: артефакт CI с master `b2137f08` (`usb-c-2key`),
наш вариант `usb-c-2key-tb6` и он же с поднятым MTU. То есть баг в текущем master,
а не в конкретном бинаре.

Совпадает с апстримным issue #152 (открыт 2026-05-28, без ответа):
*"After flashing the BadgeMagic firmware the device does not enumerate over USB at all,
(except when in ISP mode)."*

**Практическое следствие:** команда `./badge` (USB HID) после перепрошивки не работает.
Остаются BLE и режим ISP. Инструменты `badgex`/`badge` сохранены в репозитории, но
применимы только к заводской прошивке.

**Что перепрошивка даёт взамен:** часы на RTC, стриминг 30 fps на всю панель,
меню с играми, регулировку яркости по BLE, обе наши правки распиновки и MTU.
Обмен неравноценный в одну сторону - решать до прошивки, а не после.


## Предел длины анимации и как НЕ убить бейдж

Измерено 2026-09-05. Ограничение не в памяти данных, а в **оперативной**: при распаковке
слота одновременно живут сырой кусок из EEPROM и распакованный битмап.

Расход на кадр шириной 44 px: ~60.5 байт EEPROM, ~88 байт RAM распакованного битмапа,
плюс сырой кусок в тот же момент.

| Кадров | В EEPROM | Пик RAM при распаковке | Результат |
|---|---|---|---|
| 40-60 | 2.5-3.7 КБ | ~6-9 КБ | безопасно |
| **120** | **7.3 КБ** | **~17.8 КБ** | **БЕЙДЖ НЕ ЗАГРУЖАЕТСЯ** |

При 32 КБ SRAM, из которых 6 КБ забрал BLE, `malloc` на 120 кадрах возвращает `NULL`,
а `data_flash2newmem()` не проверяет результат и пишет по нулевому адресу.
Прошивка виснет в `load_bmlist()`, экран замирает на заставке FOSSASIA.

**Хранилище тут ни при чём** - 7 КБ из 32 КБ более чем достаточно. Падает распаковка.

Стриминг (`stream_bitmap`) этого ограничения не имеет вовсе: ничего не хранится
и не распаковывается, длина анимации не ограничена ничем.

Заведено апстримом: issue #195.

### Если бейдж завис на заставке

Программный вход в ISP НЕ РАБОТАЕТ: задача `SCAN_BOOTLD_BTN`, ловящая долгое `KEY2`,
регистрируется в `spawn_tasks()`, до которой выполнение не доходит. Нужен аппаратный:

1. отключить батарею, зажать `KEY2`, воткнуть USB; **либо**
2. USB воткнут, зажать `KEY2`, кратко замкнуть и отпустить `C3`

Затем:

```bash
./fix_eeprom.sh     # ждёт ISP, стирает EEPROM, сбрасывает устройство
```

Скрипт НЕ трогает кодовый флеш - ни `flash`, ни `config reset` в нём нет.
Вместе с плохой анимацией сотрутся настройки: `always-on BLE` и включённая защита.
Возврат: меню -> `SECURITY` -> `ENABLE`, затем `ble_setting [04 00 01]` + `save_cfg [06]`.

## Грабля в led-name-badge-ls32: двоеточие ломает вывод времени

`SimpleTextAndIcons.bitmap()` трактует двоеточие как синтаксис вставки иконок:

```python
text = re.sub(r':([^:]*):', replace_symbolic, text)
...
if re.match('^[0-9]*$', name):
    return chr(int(name))          # ":18:" -> chr(18)
```

Поэтому `"23:18:35"` разбирается как «символ, иконка номер 18, символ», а
`bitmap_char(chr(18))` индексирует `bitmap_preloaded`, где всего один элемент.

**Падает не всегда, а в зависимости от минуты:**

| Строка | Результат |
|---|---|
| `22:26:15` | работает - `chr(26)` совпал со встроенной иконкой |
| `12:00:00` | работает - `chr(0)` попал в нулевой элемент |
| `23:18:35` | `IndexError: list index out of range` |
| `01:02:03` | `IndexError` |

Из-за этого демо падало через раз и ровно на сцене с часами.

**Обход:** рисовать посимвольно через `bitmap_char()`, минуя разбор иконок -
так сделано в `text_cols()` в `stream_demo.py` и `anim_test.py`.
Штатная альтернатива - экранировать двоеточия удвоением: `23::18::35`.

Заодно: `bitmap_char()` отдаёт байт-столбец на символ, то есть 8 px при шрифте 5x7.
`HH:MM:SS` это 64 px, плотной упаковкой 52 - панель 44 не вмещает.
Поэтому в демо `HH:MM` рисуется крупно, а секунды идут полосой по нижней строке
(`text_cols_tight()`).
