# LED Badge CH582M

Инструменты и разбор LED-бейджа 11x44 на WCH **CH582M** (`USB 0416:5020`, BLE `LSLED`)
для macOS: управление по USB HID и Bluetooth LE на заводской прошивке, перепрошивка на
открытую [badgemagic](https://github.com/fossasia/badgemagic-firmware) и **работающие часы**.

Всё в этом файле проверено на живом устройстве, а не взято из документации.
Расхождения с чужими источниками помечены отдельно.

## Что стоит сейчас

Прошивка: `badgemagic` master `b2137f08`, вариант **usb-c-2key**
(файл `firmware/badgemagic-usb-c-2key.bin`, 188816 байт, sha256 `210a5331d3de…`).
Источник — артефакт CI прогона 33152841365. Готовый релиз `v0.1` НЕ подходил: он
«micro-USB only», а на USB-C отличается разводка пина матрицы (`PINDESC(B,6)` против
`PINDESC(B,23)`).

Заводская прошивка стёрта безвозвратно — забэкапить её было нельзя (`CFG_ROM_READ = 0`).

## Меню (2 кнопки)

```
ANIMATION | BT-PAIRING | CLOCK MODE | GAMES | SECURITY | OFF
```

| Действие | Кнопки |
|---|---|
| Листать меню | `KEY1` / `KEY2` коротко |
| Выбрать пункт | `KEY1` **долго** |
| Вернуться в меню | `KEY2` **долго** |
| Следующая картинка (в ANIMATION) | `KEY2` коротко |
| Вход в ISP для перепрошивки | `KEY2` долго (>2 с) |

Подменю CLOCK MODE: `TIME` / `STOPWATCH`. Игры: `SNAKE` / `FLAPPY` / `PONG`.

## ГЛАВНОЕ: как выставить часы

`disp_clock()` читает RTC чипа. RTC выставляется **из поля timestamp заголовка `wang`**
при каждой загрузке сообщения — `src/legacyctrl.c`:

```c
RTC_InitTime(2000 + ((d->timestamp[0] - 208 + 256) % 256),
             d->timestamp[1], d->timestamp[2],
             d->timestamp[3], d->timestamp[4], d->timestamp[5]);
```

Порядок:

1. Меню -> `BT-PAIRING`, выбрать (`KEY1` долго)
2. С компьютера: `./badgeble -m 0 "любой текст"` — вместе с картинкой уедет текущее время
3. Меню -> `CLOCK MODE` -> `TIME`

Дальше часы идут сами от RTC. Хост не нужен, износа флеша нет.

Замечание про год: наш инструмент пишет `year % 100`, а прошивка декодирует
`2000 + ((ts[0] - 208 + 256) % 256)` — год получится неверный. На отображение это не влияет,
`disp_clock()` показывает только `HH:MM`.

Иронично: это то самое поле, которое `badge-studio/PROTOCOL.md` описывает как
«The timestamp is stored but never displayed», а DeepWiki уверял, что режима часов
не существует вовсе. Проверка по исходникам master опровергла оба утверждения.

## Команды next-gen профиля (service F055 / char F057)

Обе наши прежние боли закрываются штатно:

* `ble_setting` `[0x00, 0x01]` — **always-on BLE**, затем `save_cfg` (`0x06`)

Прочее: `streaming_setting`, `stream_bitmap`, `flash_splash_screen`,
`load_fallback_cfg`, `misc` (скорость заставки, яркость 0..3).

## Если промахнулись с вариантом

Перепрошивка теперь проста: **долгое нажатие `KEY2`** вводит в ISP — без отключения
батареи и без замыкания `C3`. Другие сборки лежат в `/tmp/bmmaster/badgemagic-firmware/`
(`usb-c-4key`, `micro-b-2key`, `micro-b-4key`).

```sh

./tools/wchisp-macos-arm64/wchisp flash firmware/badgemagic-usb-c-2key.bin
```

Неверный `KEY_COUNT` не ломает железо — лишь навигация по меню будет неполной.

## Железо (снято с устройства)

USB:
```
idVendor = 0x0416   idProduct = 0x5020
USB Product Name = "CH583"   USB Vendor Name = "wch.cn"   <-- СТРОКА ВРЁТ, см. ниже
интерфейс 0: HID (class 3), usage_page = 0xFF00, usage = 0x01
USB 1.1, full speed, bMaxPacketSize0 = 64, серийного номера нет
матрица 11x44
```

BLE:
```
имя LSLED
SERVICE 0000fee0-0000-1000-8000-00805f9b34fb
  CHAR  0000fee1-0000-1000-8000-00805f9b34fb   props = read, write, notify
```

Полезная нагрузка одинакова для обоих транспортов: 64-байтный заголовок `wang`
(`77 61 6E 67`) + битмап. По BLE пишется в FEE1 кусками по 16 байт.

### Чип: CH582M, а НЕ CH583

USB-строка `CH583` — **умолчание WCH SDK, а не идентификация кремния**:
`CH5xx_ble_firmware_library/StdPeriphDriver/inc/CH58x_common.h` подключает `CH583SFR.h`
и `ISP583.h` даже при сборке под CH582. Реальный чип на плате — **CH582M**.

Подтверждения:
* владелец платы прочитал маркировку на кристалле;
* `badge-studio/PROTOCOL.md` в таблице железа: `MCU | WCH CH582`, и тут же
  `enumerates as wch.cn / CH583` — документ прямо предупреждает о расхождении;
* `badgemagic-firmware` таргетирует `CH582M`, а `wchisp` определяет чип как `CH582[0x8216]`.

Достоверный способ определить чип — `wchisp` в режиме ISP. USB-строке верить нельзя.

Реверс именно этого железа СУЩЕСТВУЕТ:
[martinbogo/badge-studio → PROTOCOL.md](https://github.com/martinbogo/badge-studio/blob/main/PROTOCOL.md)
— разбор протокола `wang` для бейджей на WCH CH582/**CH583**, с прямым указанием
`VID 0x0416 / PID 0x5020, enumerates as wch.cn / CH583`. Найден не сразу: первый поиск
дал ноль, и этот ноль был ошибочно записан как факт.

| `badge` | штатный `lednamebadge.py` по USB HID |
| `badgex` / `badgex.py` | USB + часы, повторы, `--fill8` |

Режимы: 0 влево, 1 вправо, 2 вверх, 3 вниз, 4 статично, 5 анимация, 6 сверху,
7 шторка, 8 лазер. **Рабочий диапазон 0..8.**

Кнопка на корпусе перебирает слоты: `M1`…`M8` и `M1-8` (все восемь по кругу).
В режиме `M1-8` при одном залитом слоте семь пустых — экран почти всегда пуст.
Лечится кнопкой до `M1` или ключом `--fill8`.

## Экран зарядки — разбор

* **Командой не отключается.** В 64-байтном заголовке (`LedNameBadge.header()`) есть
  яркость, мигание, рамка, скорость, режим, длины и дата — поля про зарядку нет.
  В стоковой прошивке экран зарядки крутится в блокирующем цикле, стартующем при подаче
  питания с воткнутым USB, ещё до инициализации USB-стека.
* **Кнопкой выходит, но ненадёжно** — состояние не переживает последующие записи,
  то есть для часов пришлось бы жать кнопку каждую минуту.
* **Программно кнопку нажать нельзя.** `KEY1` (PA1) и `KEY2` (PB22) — обычные GPIO-входы,
  опрашиваются прерыванием TMR3 на 50 Гц с дебаунсом. Команды эмуляции нажатия нет
  ни в USB-, ни в BLE-протоколе. Единственный «программный» путь был бы физический —
  оптрон на контакты кнопки с внешнего МК.
* `disp_charging()` **не выходит сам при полной батарее** — смотрит пин статуса заряда,
  а не уровень.
* **Поэтому решение — BLE.** Не обход, а устранение причины: нет кабеля — нет зарядки.

## Часы

```bash
./badgeble --clock --interval 60
```

Ограничение: **каждое обновление — запись во флеш бейджа**, ~1440 в сутки при минутном
интервале. Ресурс конечен; конкретной цифры для CH583 у нас нет — даташит не читали,
порог не выдумываем. Круглосуточно не оставлять, для показа на часы-другие нормально.

## Грабли

1. **CoreBluetooth убивает любой Python.** `Abort trap: 6`, termination namespace TCC:
   ни у системного, ни у brew-Python нет `NSBluetoothAlwaysUsageDescription` в Info.plist.
   Решение: копия `Python.app` с этим ключом, ad-hoc подпись, запуск **через
   LaunchServices** (`open -W -a`), чтобы TCC считал ответственным её, а не родительский
   процесс. Запуск из-под shell напрямую НЕ помогает — падает так же. Всё зашито в `badgeble`.

2. **`find_library('hidapi')` не находит библиотеку на Apple Silicon.** Homebrew кладёт её
   в `/opt/homebrew/lib`, куда `ctypes.util.find_library` не смотрит. Лечится
   `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/lib` — делают обёртки `badge` и `badgex`.

3. **По USB бейдж переэнумерируется после КАЖДОЙ записи** — HID-путь меняется
   (`...6547 → ...7563 → ...7820`), прошивка перезагружается, сохраняя во флеш.
   В этом окне устройства на шине нет, а `lednamebadge.py` делает `sys.exit`, убивая цикл.
   Закрыто в `badgex.py` через `wait_for_device()` и `send_retry()`.

4. **Успешная запись ничего не доказывает** — подтверждения от прошивки нет ни по USB,
   ни по BLE. Единственная проверка — посмотреть на экран.

5. На macOS метод `libusb` не годится: HID-интерфейс занят драйвером ядра. Только `-M hidapi`.

## Опровергнуто (проверено на этом устройстве)

* **Режимы 9 (Smooth) и 10 (Rotate) на CH583 дают ПУСТОЙ экран.** Заметка
  «Stays on, even if the cable is connected» в `doc/instructions.txt` описывает вендорское
  приложение для бейджей на **MM32L062PF** (см. `research.md` там же), а не CH583.
  Свойство было перенесено на наше железо ошибочно, три записи ушли в пустоту.
  Протокол кладёт режим в младший полубайт `h[8+i] = 16*speed + mode` и допускает 0..15,
  но прошивка CH583 знает только 0..8.

* **«Заставку удалось отключить в начале сессии»** — не было такого. Это был разовый показ
  после загрузки: устройство показывает первое сообщение один раз и возвращается к заставке.

* **«Нажатие кнопки переживает запись»** — не переживает. Вывод был сделан по одному
  удачному наблюдению без проверки цикла.

## Перепрошивка — ВОЗМОЖНА (чип совпадает)

Раз чип CH582M и матрица 11x44, наш бейдж — ровно целевая конфигурация
`fossasia/badgemagic-firmware`. Ранее в этом файле было написано «не вариант»;
это было следствием ошибочного определения чипа по USB-строке.

### Что это даёт

Две команды next-gen профиля, снимающие ОБА наших ограничения:

* `ble_setting` -> **always-on BLE** — BT-режим перестаёт выключаться после загрузки;
* `power_setting` -> **disable resetting after uploading** — уходит ребут после записи.

То есть автоматические часы становятся возможны.

### Как прошивать

Вход в ISP при заводской прошивке (один из двух способов):
1. отключить батарею, зажать `KEY2` (кнопка у разъёма USB) и воткнуть USB;
2. воткнуть USB, зажать `KEY2`, кратко замкнуть и отпустить конденсатор `C3`.

Признак ISP — одна точка в центре матрицы. Режим держится ~10 секунд.
В ISP устройство поднимается как `4348:55e0`.

```sh
wchisp config reset
wchisp flash badgemagic-ch582.bin
```

После установки открытой прошивки в ISP входят долгим нажатием `KEY2` — она
переназначает загрузочный пин в GPIO.

### Риск: он не в «кирпиче», а в необратимости

ROM-загрузчик стереть нельзя, поэтому перепрошить заново можно всегда — окончательный
кирпич маловероятен. Настоящий риск другой: **заводская прошивка защищена от чтения
(`CFG_ROM_READ = 0x0`), бэкап снять невозможно, вернуться к ней будет нельзя.**
Это билет в один конец.

Известный инцидент — issue #59: прошили бейдж с матрицей 11x55 прошивкой под 11x44
и остались без рабочего устройства и без возможности отката. У нас 11x44, то есть
именно та конфигурация, под которую собрана прошивка.

## Прочитано с устройства (2026-09-05)

### Device Information Service — заглушка из SDK

`badge-studio/PROTOCOL.md` утверждает, что стоковая прошивка вообще не публикует DIS.
У нас DIS `0x180A` есть, но он ПУСТОЙ — каждая характеристика возвращает собственное
название вместо значения:

```
Model Number      -> 'Model Number'
Manufacturer Name -> 'Manufacturer Name'
Firmware Revision -> 'Firmware Revision'
IEEE Reg. Cert.   -> fe 00 "experimental"
PnP ID            -> 01 d7 07 00 00 10 01   (VID 0x07D7, PID 0x0000, ver 0x0110)
```

Это незаполненный пример из BLE-SDK для CH58x. Вывод: прошивка заводская, собрана на
штатном WCH SDK. Это НЕ badgemagic — та отдавала бы `FOSSASIA` / `BM1144`.

### FEE1 на чтение отдаёт данные — но не режим

`badge-studio/PROTOCOL.md`: *«what those do is undocumented and unknown. Nothing has been
observed coming back from the badge on either transport.»*

У нас чтение стабильно возвращает 16 байт:

```
FEE1 read -> 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

**Гипотеза «первый байт = номер текущего режима» ПРОВЕРЕНА И ОПРОВЕРГНУТА.**
Замер: прочитали `04` после режима 4, записали режим 0, прочитали снова — снова `04`.
Значение не изменилось.

Что известно точно: два независимых чтения при разных режимах дали одинаковое `04 00...`.
Что это значит — неизвестно. Кандидаты не проверялись: версия протокола, константа
прошивки, число слотов/состояние. Для вывода нужна серия замеров с варьированием
яркости, скорости, числа сообщений и уровня батареи.

Notify включается без ошибки, но за время сессии не прислал ни одного пакета.

Вклад в общую картину скромный, но фактический: канал чтения НЕ мёртв, вопреки записи
в badge-studio. Чем он занят — открытый вопрос.

## Ограничение, закрывающее тему автоматических часов

Оба канала упираются в физическую кнопку:

| Канал | Препятствие |
|---|---|
| USB | экран зарядки; кнопка нужна после каждой записи |
| BLE | BT-режим выключается после КАЖДОЙ загрузки; кнопка нужна перед каждой отправкой |

Второе — цитата из `badge-studio/PROTOCOL.md`: *«It leaves Bluetooth mode after every
upload, so the button press has to be repeated before each send... That is expected.»*
Плюс BT-режим сам истекает через несколько минут.

Кнопки — GPIO, программно не нажимаются. **Автоматические часы на заводской прошивке
невозможны.** Снять ограничение могли бы команды badgemagic `ble_setting` (always-on BLE)
и `power_setting` (disable resetting after uploading), но это открытая прошивка под
CH582M при нашем CH583 и защищённом от чтения оригинале.

## Исправленный дефект: яркость

Байт 5 заголовка — **индекс** уровня (4 уровня: `0x00`=100%, `0x10`=75%, `0x20`=50%,
`0x30`=25%), а не битовая маска. `led-name-badge-ls32` шлёт для 25% значение `0x40` —
индекс 4 в таблице из четырёх элементов; на CH582/CH583 это портит изображение вместо
затемнения. Ошибка в апстриме с 2019 года.
Исправлено в `badgex.py` и `badge_ble.py` функцией `fix_brightness()`.
Источник: `badge-studio/PROTOCOL.md`.


## Прочитано из ISP-режима (2026-09-05, wchisp v0.3.0)

```
Chip: CH582[0x8216]   Code Flash: 448 KiB   Data EEPROM: 32 KiB
Chip UID: XX-XX-XX-XX-XX-XX-XX-XX          <- уникален для каждой платы, скрыт
BTVER (bootloader): 02.40

WPROTECT
  NO_KEY_SERIAL_DOWNLOAD  0  Disable
  DOWNLOAD_CFG            1  PB22 (Default set)
USER_CFG: 0x4FFF0F4D
  CFG_RESET_EN            1  Enable
  CFG_DEBUG_EN            0  Disable
  CFG_BOOT_EN             1  Enable
  CFG_ROM_READ            0  Disable the programmer to read out, keep the program secret
  VALID_SIG               4  Valid
```

Выводы, теперь подтверждённые на месте, а не по документам:

* **Чип — CH582, идентификатор `0x8216`.** USB-строка `CH583` была ложным следом
  (умолчание WCH SDK). Владелец платы назвал чип верно; определение по USB-строке
  было ошибкой.
* **Прошивку считать невозможно физически.** `CFG_ROM_READ = 0` — загрузчик не отдаёт
  код. Это не ограничение утилиты: у `wchisp` вообще нет команды чтения кодового флеша
  (`probe/info/reset/erase/flash/verify/eeprom/config`). Бэкап оригинала недостижим.
* **Data EEPROM пуст полностью** — все 32768 байт равны `FF` (625 строк дампа, ни одной
  с данными). Сообщения и настройки заводская прошивка хранит в защищённом кодовом флеше,
  а не в EEPROM.
* **`DOWNLOAD_CFG = PB22`** совпадает с `KEY2_PIN = PB22` в badgemagic — ещё одно
  подтверждение, что плата соответствует целевой конфигурации открытой прошивки.
* Загрузчик в ROM, `CFG_BOOT_EN = 1` — вход в ISP останется доступен всегда,
  окончательный кирпич маловероятен.

### Как войти в ISP (проверено)

Зажать `KEY2` и подать питание так, чтобы произошёл СБРОС. Просто воткнуть USB при
подключённой батарее недостаточно: без сброса загрузочный пин не опрашивается.
Окно ISP ~10 секунд, устройство поднимается как `4348:55e0`.

Ловить надо опросом самого `wchisp` в цикле: детект через `ioreg` срабатывает раньше,
чем libusb успевает поднять устройство, и одиночный вызов `wchisp` промахивается.
Рабочий скрипт — `catch_isp.sh`.

## БАГ ПРОШИВКИ: отключение SECURITY блокирует загрузку по BLE

Обнаружено на живом устройстве 2026-09-05, подтверждено по исходникам master `b2137f08`.

`src/legacyctrl.c`:

```c
static uint8_t authorized = 0;

int legacy_ble_rx(uint8_t *val, uint16_t len) {
    if (!authorized) {
        if (!memcmp(val, "wang", 4)) return -4;   // -> ATT_ERR_UNLIKELY (0x0E)
        ...
```

Проверка `!authorized` стоит БЕЗУСЛОВНО, независимо от `badge_cfg.ble_security`.
Флаг поднимается только вводом верного кода или вызовом `legacy_bypass_auth()`.

А в `src/main.c`, ветка BT-PAIRING при ВЫКЛЮЧЕННОЙ защите:

```c
} else {
    ble_enable_advertise();
    start_ble_animation();
    btn_onLongPress(KEY1, return_to_menu);   // legacy_bypass_auth() НЕ вызывается
}
```

Кода нет — вводить нечего; bypass не назначен. `authorized` остаётся нулём навсегда.
**Отключение защиты не открывает загрузку, а закрывает её.** Чинится либо
`if (badge_cfg.ble_security && !authorized)`, либо вызовом `legacy_bypass_auth()`
в неохраняемой ветке. Кандидат в issue апстрима.

Авторизация сбрасывается при разрыве связи — `legacy_reset_auth()` в
`src/ble/peripheral.c`. Поэтому обход кнопкой не доживает до следующего подключения
внешнего инструмента: PIN надо слать В ТОМ ЖЕ соединении, что и данные.

### Следствие: как выставить часы

| Канал | Авторизация | Ставит RTC |
|---|---|---|
| BLE `legacy_ble_rx()` | **требуется** | **да**, `RTC_InitTime()` из timestamp |
| USB `legacy_usb_rx()` | не требуется | **нет** |

Значит часы выставляются ТОЛЬКО по BLE и ТОЛЬКО с включённой защитой:

1. Меню -> `SECURITY` -> `ENABLE`
2. Меню -> `BT-PAIRING` -> на экране 4 цифры
3. `./badgeble --pin XXXX -m 0 "текст"` - PIN уходит первым 16-байтным пакетом,
   следом данные, всё в одном соединении

Картинки без часов можно грузить по USB вообще без кода.


## РАБОЧИЙ ПОРЯДОК синхронизации часов

```bash
./synctime 1234            # 1234 - код с экрана бейджа
./synctime 1234 "ПРИВЕТ"   # заодно залить свой текст
```

Перед этим на бейдже: меню -> `BT-PAIRING` (`KEY1` долго) -> прочитать 4 цифры.
После: меню -> `CLOCK MODE` -> `TIME`.

Повторять нужно после каждой перезагрузки бейджа: `tmos_clockInit()` безусловно
вызывает `RTC_InitTime(2020, 1, 1, 0, 0, 0)` при старте.

### Критично: дополнение пакетов нулями

`legacy_ble_rx()` отвергает ЛЮБОЙ пакет длиной != 16 байт:

```c
if (len != LEGACY_TRANSFER_WIDTH) return -1;   // -> ATT_ERR_UNLIKELY (0x0E)
```

А завершение передачи - и вызов `RTC_InitTime()` - наступает на ПОСЛЕДНЕМ пакете.
Полезная нагрузка 119 байт даёт хвост в 7 байт, он отвергается, и часы не ставятся,
хотя первые 7 пакетов прошли. Payload обязан быть кратен 16.

То же на USB: `lednamebadge.py` шлёт `range(len(buf)/64)` отчётов, неполный хвост
ОТБРАСЫВАЕТСЯ - теряются последние столбцы битмапа. Payload дополняется до кратности 64.
Оба дополнения сделаны в `badge_ble.py` и `badgex.py`.

## Ошибки, сделанные за сессию (чтобы не повторять)

Мои:
1. Режимы 9/10 «не гаснут при USB» - перенёс свойство с бейджей на MM32L062PF; на CH583/CH582 дают пустой экран.
2. «Заставку зарядки удалось отключить» - это был разовый показ после загрузки.
3. «Нажатие кнопки переживает запись» - вывод по одному наблюдению без проверки цикла.
4. «Реверса этого чипа не существует» - один поиск выдан за факт; badge-studio существует.
5. **Определил чип по USB-строке** `CH583` - это умолчание WCH SDK. Реальный чип CH582M,
   владелец платы назвал его верно. Ошибка стоила трёх отговоров от перепрошивки.
6. Исключение на последнем пакете записал в успех («штатный ребут») вместо чтения ошибки -
   скрыло настоящую причину (короткий пакет) на два круга.

Чужие источники тоже ошибались:
* `badge-studio/PROTOCOL.md`: «The timestamp is stored but never displayed» - им ставится RTC.
* `BadgeBLE.md`: описание `power_setting` инвертировано относительно кода `ngctrl.c`.
* DeepWiki: «Clock mode не существует, RTC нет» - существует, `src/main.c`.

Вывод: первичный источник - исходники и само железо. Реверс третьих лиц и ИИ-индекс - вторичны.


## Стриминг на экран в реальном времени

`stream_demo.py` — шесть сцен подряд: часы с секундами, спектр, осциллограф,
бегущая строка, «матрица», пульсирующее сердце.

```bash
./badgeble --help >/dev/null           # окружение уже готово
open -W -a ./BLEPython.app --args "$PWD/stream_demo.py"
BADGE_STREAM_COLS=44 open -W -a ./BLEPython.app --args "$PWD/stream_demo.py"
```

Перед запуском включить `BT-PAIRING` на бейдже. **Код вводить не нужно** — гейт
`!authorized` стоит только в `legacy_ble_rx()`, next-gen профиль его не проверяет.

### Чем это отличается от обычной загрузки

| | Загрузка `wang` | Стриминг `stream_bitmap` |
|---|---|---|
| Куда пишет | флеш (`data_flatSave`) | **прямо в фреймбуфер** (`tmos_memcpy(fb, ...)`) |
| Износ памяти | есть | **нет** |
| Автономность | картинка живёт без хоста | нужен постоянный поток |
| Транспорт | BLE и USB | **только BLE** |

`ng_parse()` вызывается единственным местом — `src/ble/profile/ng.c`. Оба USB-канала
(`cdc_onWrite`, `hiddev_onWrite`) заведены на `legacy_usb_rx`, пути к next-gen командам
от USB не существует.

### Формат кадра

44 слова по 16 бит, little-endian. Одно слово = один столбец, **бит 0 = верхний
пиксель**, значимы биты 0..10. Команда `0x03` первым байтом.
`streaming_setting` (`0x02`): `0x00` — войти, `0x01` — выйти.

### Измеренная пропускная способность

MTU=64, значит полезная нагрузка ATT-записи 61 байт. Полный кадр это 89 байт,
поэтому он уходит **длинной записью** — три круга вместо одного.

| Кадр | Байт | ATT | fps |
|---|---|---|---|
| 30 столбцов | 61 | одна посылка | **10.6 – 16.2** |
| 44 столбца | 89 | длинная запись | **2.7 – 4.9** |

Хуже того, полноширинный поток **рвёт соединение через 25–30 с**: длинные записи
копятся в пуле `BLE_BUFF_NUM = 512/23 = 22`, и стек сбрасывает линк. Об этом прямо
предупреждает комментарий в `src/ble/setup.c`. Поток в 30 столбцов отработал 41 с
без обрыва, средний 14.9 fps.

Причина одна: `F057` объявлена как `GATT_PROP_WRITE` без `GATT_PROP_WRITE_NO_RSP`
(`src/ble/profile/ng.c`). Заведено апстримом: issue #192.

Обход на сегодня — гнать 30 столбцов, предварительно один раз очистив все 44.


## Плата с нестандартной комбинацией пинов матрицы (решено)

**Симптом:** две колонки (39 и 40, считая с единицы) не горят никогда — ни в стриминге,
ни при обычной загрузке картинки. Остальная панель работает.

**Причина:** `src/leddrv.c` переключает три пина одним флагом `HARDWARE_REV3`:

| Буква | Индекс | Пара развёртки | Колонки (с 0) | default | REV3 |
|---|---|---|---|---|---|
| J | 9 | 9 | 18, 19 | B15 | B17 |
| K | 10 | 10 | 20, 21 | B14 | B16 |
| T | 19 | 19 | **38, 39** | **B23** | **B6** |

Наша плата требует `T` как в REV3, а `J` и `K` — как в дефолте. Такой комбинации среди
готовых сборок нет: `HARDWARE_REV3` меняет все три сразу, и вместо двух мёртвых колонок
получилось бы шесть.

**Как измерено.** Кадр зажигает ровно две колонки за раз (`diag_edge.py`), плюс узор из
пяти блоков по 4 колонки с промежутками по 5 (`diag_blocks.py`). Видно, что мертва ровно
одна пара — 38 и 39, то есть пара развёртки 19, драйвер `led_pins[19] = T`.
Колонки 18–21 (пины J, K) и 42–43 исправны.

**Решение:** форк с флагом `LED_PIN_T_B6`, выбирающим пин `T` отдельно от остальных:
https://github.com/NickoScope/badgemagic-firmware/tree/hw-rev2-t-b6

```c
#if defined(HARDWARE_REV3) || defined(LED_PIN_T_B6)
	PINDESC(B, 6), // T
#else
	PINDESC(B, 23), // T
#endif
```

Сборка варианта `usb-c-2key-tb6` добавлена в CI. Готовый бинарь:
`firmware/badgemagic-usb-c-2key-tb6.bin`, sha256 `566cb93f731cafd4…`.
После прошивки все 44 колонки работают — проверено.

**Тупики, пройденные по дороге** (чтобы не повторять): грешил на длинные записи BLE,
на потерю ATT-фрагмента, на дополнение кадра нулями и на ревизию платы целиком.
Все четыре версии звучали стройно и все были неверны. Развязало дело только одно —
зажигать по две колонки за раз и спрашивать «горит или нет».


## Полноскоростной стриминг: 30 fps на всю панель (решено)

Штатная прошивка ограничивала MTU: `src/ble/setup.c`, `BLE_BUFF_LEN (64 + 4)`.
При MTU 64 полезная нагрузка ATT-записи - 61 байт, а полный кадр это
`1 + LED_COLS*2 = 89`. Каждый кадр уходил длинной записью: три круга вместо
одного, накопление в пуле `BLE_BUFF_NUM` и обрыв связи через 25-30 с.

Правка - пять строк в двух файлах:

```diff
- #define BLE_BUFF_LEN (64 + 4)
+ #define BLE_BUFF_LEN (128 + 4)

- static uint8_t RxCharProps = GATT_PROP_WRITE;
+ static uint8_t RxCharProps = GATT_PROP_WRITE | GATT_PROP_WRITE_NO_RSP;
```

Одного `GATT_PROP_WRITE_NO_RSP` НЕДОСТАТОЧНО: `Write Command` ограничен `ATT_MTU-3`
и длинной формы не имеет, поэтому без подъёма потолка кадр в 89 байт всё равно
не пройдёт одной посылкой. Нужны обе правки.

### Результат, измерено на устройстве

| Режим | fps | Панель | Разрыв картинки | Обрывы связи |
|---|---|---|---|---|
| `fast30` | 14.9 | четверть статична | нет | нет |
| `hybrid` | 9.3 | вся | **есть** | нет |
| `full44` до правки | 4.7 | вся | нет | **раз в 30 с** |
| **`full44` после** | **30.0** | **вся** | **нет** | **нет** |

30 fps - это заданный клиентом потолок, а не предел железа (`BADGE_FPS`).

### Важно на стороне клиента

Запись без подтверждения не даёт обратной связи, вместе с ней исчезает и
естественное торможение. Без ограничения темпа цикл забивает очередь стека
быстрее, чем она отправляется: первый прогон показал 86000 «кадров» в секунду
и зависание на 22 секунды. Темп задаёт клиент - см. `target_fps` в `stream_demo.py`.

Прошивка: форк `hw-rev2-t-b6`, файл `firmware/badgemagic-usb-c-2key-tb6-mtu128.bin`,
sha256 `58a811814d9ca6e7…`. Предыдущая рабочая версия сохранена как `...-PREV.bin`.


## BT-PAIRING нужен НЕ ВСЕГДА

Проверено 2026-09-05: бейдж рекламируется постоянно, без входа в режим сопряжения.
Причина - включённый и сохранённый `always-on BLE` (`ble_setting [04 00 01]` + `save_cfg`).
Настройка живёт в **Data EEPROM**, отдельной от кодового флеша, поэтому пережила
обе перепрошивки: `wchisp flash` пишет только код, `config reset` трогает регистры чипа.

| Что делаем | Профиль | Нужен BT-PAIRING | Нужен PIN |
|---|---|---|---|
| Стриминг `stream_bitmap` | next-gen F055/F057 | **нет** | **нет** |
| Яркость, настройки, `save_cfg` | next-gen F055/F057 | **нет** | **нет** |
| Загрузка картинки `wang` | legacy FEE0/FEE1 | **да** | **да** |

Гейт `!authorized` стоит только в `legacy_ble_rx()`. Next-gen профиль его не проверяет,
поэтому всё потоковое и конфигурационное работает с любого места - хоть из меню,
хоть из режима ANIMATION.

BT-PAIRING остаётся нужен лишь для обычной загрузки картинок: только там генерируется
четырёхзначный код, без которого `legacy_ble_rx()` отвергает пакет с `wang`.
Поэтому и синхронизация часов (`./synctime`) по-прежнему требует кода - RTC ставится
именно из legacy-заголовка.
