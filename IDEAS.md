# Задел на будущее

## Бейдж как игровая консоль: кнопки как события по BLE

**Идея.** Экран и кнопки — на бейдже, вся логика — на хосте. Тогда бейдж
становится полноценным контроллером: платформер с прыжком по кнопке, змейка,
пинг-понг, меню с выбором — что угодно, где нужна обратная связь.

Сейчас есть только половина: кадры уходят на бейдж со скоростью 30 fps
(`stream_bitmap`), а обратно не приходит ничего.

### Почему сейчас не работает

**Канал от бейджа к хосту существует, но занят другим.** `ng_notify()` вызывается
ровно в одном месте — `src/ngctrl.c`, `ng_parse()`:

```c
uint8_t ret = (*cmd_lut[cmd])(val + 1, len - 1);
ng_notify(&ret, 1);   // ответ на присланную команду, и только
```

О нажатиях прошивка не сообщает никак. Кнопки — обычные GPIO
(`KEY1` = PA1, `KEY2` = PB22), опрашиваются прерыванием TMR3 на 50 Гц
с программным дебаунсом, и обрабатываются внутри.

**Вторая помеха.** В режиме стриминга `streaming_setting(0x00)` вызывает
`stop_all_animation()`, но привязки кнопок не трогает. Они остаются от текущего
режима — то есть нажатие `KEY1` в меню вызовет `menu_up()`, который перерисует
меню поверх нашей картинки.

### Что сделать в прошивке

Форк уже есть: https://github.com/NickoScope/badgemagic-firmware ветка `hw-rev2-t-b6`

**1. Перепривязать кнопки на время стриминга.** В `streaming_setting()`
(`src/ngctrl.c`) при входе сохранить текущие обработчики и поставить свои,
которые ничего не рисуют, а только шлют событие; при выходе — вернуть.

```c
static void key_event(uint8_t code) {
    uint8_t ev[2] = {0xE0, code};
    ng_notify(ev, sizeof(ev));
}
// вход в стриминг:
btn_onOnePress(KEY1, ev_key1_down);
btn_onOnePress(KEY2, ev_key2_down);
btn_onLongPress(KEY1, ev_key1_long);
btn_onLongPress(KEY2, ev_key2_long);   // выход оставить за KEY2 долгим?
```

Осторожно с выходом: если отдать ВСЕ кнопки хосту, из режима стриминга нельзя
будет выйти без хоста. Разумно оставить `KEY2` долгим за возврат в меню.

**2. Формат события.** Префикс `0xE0` отличает событие от кода возврата команды
(тот всегда один байт). Второй байт — что произошло:

```
0xE0 0x01  KEY1 нажата
0xE0 0x02  KEY2 нажата
0xE0 0x11  KEY1 долгое нажатие
0xE0 0x12  KEY2 долгое нажатие
```

**3. Ничего не ломается для существующих клиентов**: кто не подписан на notify,
событий не увидит; кто подписан ради кодов возврата — отличит их по префиксу.

### Что сделать в пакете rpi/

`badge/ble.py` уже умеет `enable_notify(cb)`. Нужно:

* разбирать события `0xE0 ...` и класть в `asyncio.Queue`;
* дать источникам доступ к вводу — например `Source.on_key(code)` или
  очередь в `run(out, stop, keys)`;
* в `Platformer` заменить автопрыжок на прыжок по `KEY1`, оставив
  автоматический режим как демонстрационный (`opts["auto"]`).

### Как проверить

1. Собрать вариант через CI форка, скачать артефакт, прошить долгим `KEY2`.
2. Подписаться на `F056`, войти в стриминг, нажать `KEY1` — в логе должно
   появиться `E0 01`.
3. Замерить задержку: кнопка опрашивается на 50 Гц, интервал соединения BLE
   обычно 30-50 мс, значит реакция ожидается в пределах 60-80 мс. Для платформера
   этого достаточно.

### Зачем это апстриму

Сейчас `F056` умеет только отдавать коды возврата. Событийный канал сделал бы
next-gen профиль **двусторонним** — и открыл бы класс применений, которого
у прошивки пока нет: игры с управлением, интерактивные меню, бейдж как пульт
для чего угодно на хосте. Это заметно больше, чем наши предыдущие правки,
и просилось бы отдельным PR с обсуждением формата событий.

### Оценка

Прошивка — строк тридцать. Клиент — примерно столько же. Сборка, прошивка
и проверка отработаны: около двадцати минут вместе со всем.

## Что попроще, если руки дойдут

* **Управление с клавиатуры Mac прямо сейчас** — экран на бейдже, прыжок по
  пробелу. Работает без единой правки прошивки.
* **Игры на хосте**: змейка, пинг-понг, тетрис на 44x11 — вся логика в
  `sources.py`, рисование уже есть.
* **Часы по MQTT из Home Assistant** — источник `mqtt` готов, нужен только топик.
* **Уведомления**: почта, календарь, CI — бегущей строкой через `badgectl stream stdin`.
