# Задел на будущее

## Бейдж как игровая консоль: кнопки как события по BLE

**Идея.** Экран и кнопки — на бейдже, вся логика — на хосте. Тогда бейдж
становится полноценным контроллером: платформер с прыжком по кнопке, змейка,
пинг-понг, меню с выбором — что угодно, где нужна обратная связь.

Сейчас есть только половина: кадры уходят на бейдж со скоростью 30 fps
(`stream_bitmap`), а обратно не приходит ничего.

### Почему сейчас не работает

**Канал от бейджа к хосту существует, но занят другим.** `ng_notify()` вызывается
ровно в одном месте — `src/ngctrl.c`, `ng_parse()`:

```c
uint8_t ret = (*cmd_lut[cmd])(val + 1, len - 1);
ng_notify(&ret, 1);   // ответ на присланную команду, и только
```

О нажатиях прошивка не сообщает никак. Кнопки — обычные GPIO
(`KEY1` = PA1, `KEY2` = PB22), опрашиваются прерыванием TMR3 на 50 Гц
с программным дебаунсом, и обрабатываются внутри.

**Вторая помеха.** В режиме стриминга `streaming_setting(0x00)` вызывает
`stop_all_animation()`, но привязки кнопок не трогает. Они остаются от текущего
режима — то есть нажатие `KEY1` в меню вызовет `menu_up()`, который перерисует
меню поверх нашей картинки.

### Что сделать в прошивке

Форк уже есть: https://github.com/NickoScope/badgemagic-firmware ветка `hw-rev2-t-b6`

**1. Добавить отпускание в `button.c`.** Сейчас `button.h` предлагает только
`btn_onOnePress()` и `btn_onLongPress()` — события отпускания нет:

```c
void btn_onOnePress(int key, void (*handler)(void));
void btn_onLongPress(int key, void (*handler)(void));
```

Нужен `btn_onRelease(int key, void (*handler)(void))` рядом с ними, на том же
конечном автомате дебаунса. Опрос уже идёт в `btn_tick()` от прерывания TMR3
на 50 Гц, а `isPressed(key)` читает пин напрямую — состояние есть, не хватает
только обратного фронта.

**2. Слать НАЖАТИЕ и ОТПУСКАНИЕ, а не «нажал» и «долго нажал».**

Это принципиально. С парой press/long-press набор жестов зафиксирован в прошивке
навсегда: захочешь добавить двойное нажатие или аккорд — надо перепрошивать бейдж.
С парой down/up прошивка сообщает только физику, а семантику решает хост:

* длительность удержания меряет хост — долгое нажатие становится настройкой игры,
  а не константой прошивки;
* одновременное нажатие двух кнопок хост видит сам и может считать третьей командой;
* автоповтор при удержании — тоже на хосте;
* двойное нажатие, ритмические комбинации, что угодно — без правки прошивки.

Прошивке не надо знать, что такое «долгое нажатие». Её дело — фронты.

```c
static void key_event(uint8_t code) {
    uint8_t ev[2] = {0xE0, code};
    ng_notify(ev, sizeof(ev));
}
```

Формат события. Префикс `0xE0` отличает его от кода возврата команды — тот
всегда однобайтовый, так что существующие клиенты не сломаются:

```
0xE0 0x01   KEY1 нажата
0xE0 0x81   KEY1 отпущена      (старший бит = отпускание)
0xE0 0x02   KEY2 нажата
0xE0 0x82   KEY2 отпущена
```

**3. Перепривязать кнопки на время стриминга.** Изобретать нечего — в прошивке
уже есть готовый образец. `src/game.c` (змейка) делает ровно это:

```c
void game_start(uint16_t *fb)
{
    game_fb = fb;
    ...
    btn_onOnePress(KEY1, on_turn_left);     // просто переприсваивание
    btn_onOnePress(KEY2, on_turn_right);
    tmos_start_task(game_taskid, GAME_TICK, MS_TO_TMOS(speed_ms));
}
```

а выход `game_exit()` вызывает `return_to_menu()`, который возвращает привязки
меню обратно. Нам нужно то же самое, только вместо игровой логики — `ng_notify()`.

Полезное из того же файла:

* **змейка на двух кнопках** использует ОТНОСИТЕЛЬНЫЙ поворот, «влево от себя»
  и «вправо от себя», с защитой от разворота: `if (next_dir != (cur_dir + 2) % 4)`.
  Подтверждает, что двух кнопок хватает без потерь;
* игровой цикл — **самоперезапускающаяся задача TMOS**, а не блокирующий `while`;
* игра пишет **в тот же `fb`**, в который льём мы. Значит во время стриминга
  игра на бейдже идти не должна — конкуренция за один буфер;
* рекорд хранится в EEPROM по `0x7FF8` — в той самой памяти, которую слишком
  длинная анимация затирает (issue #195).

Итого В `streaming_setting()`
(`src/ngctrl.c`) при входе сохранить текущие обработчики и поставить свои —
которые ничего не рисуют, а только шлют события; при выходе вернуть как было.

Осторожно с выходом: если отдать хосту ВСЕ кнопки, из режима стриминга нельзя
будет выйти без хоста, и бейдж окажется в ловушке. Разумно оставить `KEY2`
долгим за возврат в меню — либо, что честнее, выходить по потере BLE-связи.

### Что сделать в пакете rpi/

`badge/ble.py` уже умеет `enable_notify(cb)`. Нужно:

* разбирать события `0xE0 ...` и класть в `asyncio.Queue`;
* держать состояние кнопок (`down`/`up`) и время последнего фронта — из этого
  хост сам выводит долгое нажатие, двойное, аккорд и автоповтор;
* дать источникам доступ к вводу — например `Source.on_key(code, down)` или
  очередь в `run(out, stop, keys)`;
* в `Platformer` заменить автопрыжок на прыжок по `KEY1`, оставив
  автоматический режим как демонстрационный (`opts["auto"]`).

### Как проверить

1. Собрать вариант через CI форка, скачать артефакт, прошить долгим `KEY2`.
2. Подписаться на `F056`, войти в стриминг, нажать `KEY1` — в логе должно
   появиться `E0 01`.
3. Замерить задержку кругом: кнопка опрашивается на 50 Гц (20 мс), интервал
   соединения BLE обычно 30-50 мс, плюс обработка на хосте и кадр обратно.
   Ожидание — **80-130 мс на полный круг**. Для бегуна, змейки и арканоида
   достаточно; для игр с окном попадания меньше 50 мс — нет.

### Что из этого можно сделать

Двух кнопок хватает на больше, чем кажется. Змейка играется поворотом
«влево от себя» и «вправо от себя» — badgemagic именно так и сделал в своей
2-кнопочной сборке, ничего не потеряв. Дальше: бесконечный бегун, Flappy,
арканоид, пинг-понг, слалом, уклонение, реакция, «Саймон говорит», викторины
и текстовые развилки, тетрис (поворот и сдвиг, падение удержанием).

Чего не выйдет: игр с точностью до 50 мс — не позволит круг задержки; игр,
где нужна картинка — на одиннадцати пикселях по высоте персонаж это четыре
точки; и всего с четырьмя направлениями сразу без модальности.

### Зачем это апстриму

Сейчас `F056` умеет только отдавать коды возврата. Событийный канал сделал бы
next-gen профиль **двусторонним** — и открыл бы класс применений, которого
у прошивки пока нет: игры с управлением, интерактивные меню, бейдж как пульт
для чего угодно на хосте. Это заметно больше, чем наши предыдущие правки,
и просилось бы отдельным PR с обсуждением формата событий.

### Оценка

Прошивка — строк тридцать. Клиент — примерно столько же. Сборка, прошивка
и проверка отработаны: около двадцати минут вместе со всем.

## Что попроще, если руки дойдут

* **Управление с клавиатуры Mac прямо сейчас** — экран на бейдже, прыжок по
  пробелу. Работает без единой правки прошивки.
* **Игры на хосте**: змейка, пинг-понг, тетрис на 44x11 — вся логика в
  `sources.py`, рисование уже есть.
* **Часы по MQTT из Home Assistant** — источник `mqtt` готов, нужен только топик.
* **Уведомления**: почта, календарь, CI — бегущей строкой через `badgectl stream stdin`.
